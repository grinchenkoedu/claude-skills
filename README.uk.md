Навички (skills) для [Claude Code](https://claude.com/claude-code), які покривають
звичайний робочий день розробника: зрозуміти, що саме треба зробити, зробити це, перевірити
власну роботу, відрецензувати чужий пул-реквест, опрацювати коментарі до свого та переконатися,
що результат справді працює.

Вони працюють у будь-якому репозиторії — тут немає нічого, прив'язаного до конкретного проєкту,
мови чи фреймворку. Їх також написано **ощадливими**, щоб ними було зручно користуватися на
скромному тарифі Claude: жодних фонових роїв агентів, жодних паралельних субагентів за
замовчуванням, а відповіді — у чаті, а не купою згенерованих звітів.

## Що це таке

**Навичка (skill)** — це набір інструкцій, який можна викликати за назвою в Claude Code.
Замість того щоб щоразу пояснювати, як має виглядати добра рецензія коду, ви пишете `/gku:review`,
і Claude виконує процедуру, яку написали один раз і відшліфували.

Викликаються вони через скісну риску, наприклад `/gku:review`, у чаті Claude Code.

Це **не магія** і **не автоматика**. Кожна з них робить те, що ви могли б зробити й самі, —
просто робить це послідовно й не забуває нудних дрібниць, а саме звідти й беруться помилки.

Чотири з них (`/gku:plan`, `/gku:review`, `/gku:pr-review`, `/gku:verify`) взагалі не змінюють ваш
код. Три (`/gku:implement`, `/gku:fix`, `/gku:pr-resolve`) змінюють — і кожна повідомляє, що саме
збирається зробити. `/gku:pr` локально не змінює нічого: він надсилає вже зроблені вами коміти й
відкриває пул-реквест.

## Що потрібно перед початком

1. **Claude Code**, встановлений і робочий — [інструкція зі встановлення](https://docs.claude.com/en/docs/claude-code/overview).
2. **git** — він у вас уже є, якщо ви клонуєте репозиторії.
   **На Windows встановіть [Git for Windows](https://git-scm.com/download/win)** — він містить
   Git Bash. Claude Code запускає команди через нього, і ці навички розраховують, що він є.
3. **GitHub CLI (`gh`)** — для трьох навичок, що працюють із пул-реквестами:

   ```bash
   winget install --id GitHub.cli     # Windows
   brew install gh                    # macOS
   sudo apt install gh                # Ubuntu/Debian
   ```

   Далі один раз увійти й перевірити, що спрацювало:

   ```bash
   gh auth login
   gh auth status
   ```

   `/gku:plan`, `/gku:implement`, `/gku:review`, `/gku:fix` і `/gku:verify` працюють без `gh`. Він
   потрібен лише для `/gku:pr`, `/gku:pr-review` та `/gku:pr-resolve`, бо вони звертаються до GitHub.

4. **Docker** — [Docker Desktop](https://www.docker.com/products/docker-desktop/) на Windows і
   macOS, Docker Engine на Linux. **Наполегливо рекомендовано на кожній платформі**, не лише на
   Windows.

   Навички за замовчуванням виконують команди проєкту **всередині його контейнера**. Річ не в
   зручності, а в правильності: ці проєкти розраховані на конкретні версії середовища. Плагін,
   написаний під PHP 7.4, але перевірений хостовим PHP 8.4, спокійно пропустить синтаксис, який
   зламається на продакшені, а набір тестів, що пройшов на неправильній версії, нічого не
   довів. У контейнері — та сама версія, що й у проєкті, разом із залежностями та базою даних.

   Це також означає, що вам не потрібні локально ані PHP, ані Composer, ані Python чи Node —
   кілька з цих проєктів прямо виходять із того, що їх у вас немає, — і ті самі команди
   однаково працюють на Windows, macOS, Linux і WSL.

   Без Docker навички теж працюють: вони перейдуть на те, що є на вашій машині, і повідомлять
   про це. Якщо версії відрізняються від проєктних — ставтеся до «зеленого» результату з
   недовірою.

**Windows працює.** Використовуйте Git Bash, як у пункті 2. Навички визначають платформу під час
першого запуску й зберігають команди, які на ній працюють. WSL теж працює й поводиться як Linux.

## Встановлення

У Claude Code виконайте дві команди:

```
/plugin marketplace add grinchenkoedu/claude-skills
/plugin install gku@grinchenkoedu
```

Це все. Наберіть `/` — і побачите у списку `/gku:plan`, `/gku:implement`, `/gku:review`,
`/gku:fix`, `/gku:pr`, `/gku:pr-review`, `/gku:pr-resolve` та `/gku:verify`.

### Оновлення

Навички регулярно покращуються. Щоб отримати найновіші:

```
/plugin marketplace update grinchenkoedu
/reload-plugins
```

Перша команда оновлює маркетплейс із GitHub, друга перезавантажує навички в поточній сесії, тож
перезапускати нічого не треба.

Якщо не хочеться про це думати, `/plugin` відкриває менеджер, де видно встановлене й можна
оновити звідти.

**Чому оновлення приходять завжди:** цей плагін навмисно не має поля `version` у маніфесті.
Тоді Claude Code вважає **кожен коміт новою версією**, тож оновлення завжди приносить найсвіжіше.
Якби версію було вказано, ви не отримували б нічого до її підняття — а забуте підняття означає,
що ви місяцями непомітно користуєтесь старими навичками.

<details>
<summary>Якщо ви встановлювали копіюванням файлів</summary>

Скопіюйте їх заново — ніщо не відстежує джерело:

```bash
cd claude-skills && git pull
cp -R plugins/gku/skills/* ~/.claude/skills/
cp -R plugins/gku/reference ~/.claude/skills/reference
cp -R plugins/gku/templates ~/.claude/skills/templates
```

Це головна причина віддати перевагу встановленню через плагін.
</details>

<details>
<summary>Встановлення без системи плагінів</summary>

macOS, Linux або Git Bash на Windows:

```bash
git clone https://github.com/grinchenkoedu/claude-skills.git
mkdir -p ~/.claude/skills
cp -R claude-skills/plugins/gku/skills/* ~/.claude/skills/
cp -R claude-skills/plugins/gku/reference ~/.claude/skills/reference
cp -R claude-skills/plugins/gku/templates ~/.claude/skills/templates
```

Windows PowerShell:

```powershell
git clone https://github.com/grinchenkoedu/claude-skills.git
New-Item -ItemType Directory -Force "$HOME\.claude\skills" | Out-Null
Copy-Item -Recurse -Force claude-skills\plugins\gku\skills\* "$HOME\.claude\skills\"
Copy-Item -Recurse -Force claude-skills\plugins\gku\reference "$HOME\.claude\skills\reference"
Copy-Item -Recurse -Force claude-skills\plugins\gku\templates "$HOME\.claude\skills\templates"
```

Через плагін оновлювати простіше. Цей спосіб — лише якщо є причина.

> **Дві відмінності цього способу.** Навички **не отримують префікса** — вони встановлюються як
> `/review`, `/init`, `/verify`, а не `/gku:review`. Це означає, що **`/init`, `/review` і
> `/verify` заміщають однойменні команди самого Claude Code**, причому `/init` виконує схоже
> завдання, тож ви не зрозумієте, яку саме викликали. Перейменуйте каталоги в
> `~/.claude/skills/`, якщо хочете зберегти оригінальні команди.
</details>

## Навички

Вони йдуть у порядку самої роботи:

```
   /gku:init ──▶ /gku:plan ──▶ /gku:implement ──▶ /gku:review ⇄ /gku:fix ──▶ /gku:pr
(раз на репозиторій)                                                            │
                                       ┌────────────────────────────────────────┤
                                       ▼                                        ▼
                                /gku:pr-review                          /gku:pr-resolve
                            (чужий пул-реквест)                 (коментарі до вашого)
                                       │                                        │
                                       └───────────────▶ /gku:verify ◀──────────┘
```

| Команда | Що робить | Змінює код? |
|---|---|---|
| `/gku:init` | Створює `CLAUDE.md` цього репозиторію — команди та правила його родини | **Так** (один файл) |
| `/gku:plan` | Перетворює запит на конкретний план, звірений із реальним кодом | Ні |
| `/gku:implement` | Виконує план крок за кроком, відмічаючи прогрес | **Так** |
| `/gku:review` | Перевіряє ваші власні зміни перед відправкою | Ні |
| `/gku:fix` | Виправляє те, що знайшла рецензія, — один коміт на одну знахідку | **Так** |
| `/gku:pr` | Відкриває пул-реквест для цієї гілки або оновлює наявний | Ні (надсилає ваші коміти) |
| `/gku:pr-review` | Ретельно рецензує чужий пул-реквест | Ні |
| `/gku:pr-resolve` | Опрацьовує коментарі рецензентів до *вашого* пул-реквесту | **Так** |
| `/gku:verify` | Запускає тести й перевіряє, що воно справді працює | Ні |

Не обов'язково користуватися всіма чи саме в цьому порядку. Сам лише `/gku:review` перед кожною
відправкою вже вартий того.

## Приклад від початку до кінця

Припустімо, вам повідомили: *експорт статистики об'єднує дві кафедри, які мають однакову назву.*

**1. З'ясувати, у чому насправді річ.**

```
/gku:plan експорт статистики об'єднує кафедри з однаковою назвою
```

> **Про лапки:** вони не потрібні. Те, що ви пишете, передається навичці як звичайний текст —
> жодної оболонки (shell) тут немає, тож нічого не треба екранувати, і апострофи теж не
> заважають. Лапки варті того лише тоді, коли після опису йде прапорець — щоб позначити, де
> опис закінчується: `/gku:implement "додати експорт у CSV" --continue`.

Claude знайде код експорту, прочитає його, перевірить у базі, чи справді існують однойменні
кафедри, і запише план у `.tasks/export-department-collision.md` — із причиною, виправленням,
критеріями готовності та впорядкованими кроками. Прочитайте його. **Якщо план хибний — скажіть
про це зараз:** виправити план значно дешевше, ніж наполовину зроблену зміну.

**2. Зробити.**

```
/gku:implement .tasks/export-department-collision.md
```

Створить гілку, пройде кроки по черзі, відмітить кожен у файлі задачі й запустить тести. Ви
бачите кожну правку й можете зупинити будь-якої миті.

> **Якщо ліміт використання скінчиться посеред роботи — це не проблема.** Виконані кроки вже
> відмічені у файлі задачі. Коли ліміт поновиться,
> `/gku:implement .tasks/export-department-collision.md --continue` продовжить рівно з того місця,
> де зупинився.

**3. Перевірити власну роботу.**

```
/gku:review
```

Ви отримаєте короткий перелік: блокери, які треба виправити, попередження, на які варто
глянути, і дрібниці, які можна проігнорувати. Наприкінці навичка називає наступну команду — щоб
ви не лишалися сам на сам зі списком.

**4. Виправити знайдене.**

```
/gku:fix
```

Бере знахідки з рецензії, яку ви щойно запустили, **звіряє кожну з реальним кодом** перед тим
як щось чіпати — щось уже виявиться виправленим, а щось просто хибним, — а тоді виправляє
блокери й попередження, по коміту на кожне, і перезапускає тести. Дрібниці лише перелічує;
щоб узяти і їх, додайте `--nits`.

**5. Відкрити пул-реквест.**

```
/gku:pr
```

Читає гілку цілком, перевіряє, що вона **читається як один пул-реквест** — і спершу питає, якщо
це схоже на фічу з причепленим стороннім виправленням, — потім надсилає коміти й пише опис із
реального діфу, за шаблоном вашого репозиторію, якщо він є.

**6. Опрацювати коментарі рецензії.**

Автоматичний рецензент залишив коментарі. Замість виправляти кожен вручну:

```
/gku:pr-resolve 42
```

Спочатку **звіряє кожен коментар із реальним кодом**, потім виправляє те, що справді
слушне, аргументовано заперечує там, де рецензент помилився, і питає вас про те, що
неоднозначне. Один коміт на одне виправлення, одна відповідь на один коментар.

**7. Переконатися, що працює.**

```
/gku:verify
```

Запустить тести *і* власне сам експорт, а тоді дасть висновок — разом із чесним переліком
того, що перевірити не вдалося.

## Кожна навичка докладно

### `/gku:init` — створити `CLAUDE.md` для репозиторію

```
/gku:init
/gku:init --refresh
/gku:init --dry-run
```

`CLAUDE.md` читається на початку кожної сесії в репозиторії, тож саме там мають бути команди
збірки й тестів і ті кілька правил, які тут справді порушують. `/gku:init` визначає родину проєкту —
плагін Moodle, PHP-застосунок, CMS, Python — підставляє справжні команди й додає домовленості та
правила безпеки цієї родини.

Спільна частина лежить між маркерами:

```markdown
<!-- toolkit:begin family-rules -->
...підтримується /gku:init...
<!-- toolkit:end family-rules -->
```

`--refresh` замінює **лише** цей блок, тож написане вами руками зберігається.

Якщо `CLAUDE.md` уже існує, його спершу **читають і оцінюють**: якщо команди правильні, а блок
родини актуальний, ви отримаєте відповідь «вже все гаразд» і жодного запису — переписувати
добрий файл не є покращенням. Застарілу команду або правило, якому суперечить код, буде
перелічено для вас, а не мовчки виправлено. Файл без маркерів ніколи не перезаписується.

Також створюється заглушка `AGENTS.md` з посиланням на `CLAUDE.md`, щоб інші агенти знаходили ті
самі правила без другої копії, яка розходиться. Саме заглушка, а не символьне посилання: у
Windows git вивантажує символьні посилання як звичайні текстові файли.

Запустіть один раз на репозиторій і ще раз, коли правила родини покращаться.

### `/gku:plan` — зрозуміти, що робити

```
/gku:plan студенти не можуть завантажити свій індивідуальний план
/gku:plan .tasks/new-grade-export.md
/gku:plan --review .tasks/proposed-approach.md
```

Дайте їй речення або вкажіть markdown-файл із докладнішим описом. Вона визначить, про що
йдеться — про помилку, нову можливість, питання чи проблему з даними (це потребує зовсім різних
відповідей), — а тоді прочитає код і звірить свої припущення з реальними даними, перш ніж щось
пропонувати.

Результат — `.tasks/<назва>.md`: причина або дизайн, критерії готовності, впорядковані кроки й
те, як перевірити результат.

`--review` — коли у файлі **вже запропоновано** рішення: тоді навичка оцінює цю пропозицію, а
не вигадує власну.

**Код не пишеться.** Користуйтесь, коли ще не певні, яка зміна правильна. Для очевидного
виправлення в один рядок — пропустіть цей крок.

### `/gku:implement` — зробити

```
/gku:implement .tasks/export-department-collision.md
/gku:implement додати експорт студентів у CSV
/gku:implement .tasks/big-task.md --continue
```

Працює послідовно у вашому робочому каталозі — без фонових агентів, нічого не приховано.
Створить гілку, якщо ви на головній, пройде кроки по черзі, перевірятиме кожну зміну одразу,
напише тести й запустить набір тестів.

**Файл задачі водночас є журналом прогресу.** Кожен виконаний крок відмічається з поміткою, що
саме зроблено, — саме завдяки цьому працює `--continue` після перерви.

Навичка тримається межі задачі. Якщо помітить щось інше поламане — скаже наприкінці, а не
виправить нишком: зміна, яка розповзається, стає такою, що її неможливо відрецензувати.

### `/gku:review` — перевірити власну роботу

```
/gku:review
/gku:review --deep
/gku:review --report
```

**Та, якою варто користуватися щодня.** Запускайте перед відправкою змін. Вона прочитає ваші
зміни, застосує домовленості *вашого* репозиторію (з `AGENTS.md`, `CLAUDE.md` чи що там є в
проєкті) і видасть перелік за рівнем важливості:

- **BLOCKER** — не відправляйте. Закомічений пароль, втрата даних, перейменована функція, яку
  досі десь викликають, неекранований користувацький ввід, зміна в Moodle без підняття
  `version.php`.
- **WARNING** — виправте, перш ніж просити рецензію. Логіка без тестів, необроблений шлях
  помилки, цикл, який може не завершитися.
- **NIT** — на ваш розсуд.

Вона також перевіряє, чи ваші **тести справді щось доводять**: тест без реального твердження
або такий, що замокав саме те, що ви змінили, проходить, нічого не доводячи.

Якщо у проєкті є команда лінтера, вона **перевіряє змінені вами файли** й повідомляє про
синтаксичну помилку як про блокер. У репозиторії без тестів і без робочого CI це єдина
механічна перевірка між синтаксичною помилкою та робочим сайтом. Вона також попередить, якщо
лінтер працює на новішій версії мови, ніж та, під яку написано проєкт: успішна перевірка
парсером PHP 8 нічого не доводить про проєкт, який декларує `>=7.4`.

`--deep` дозволяє одному помічнику додатково перевірити, хто викликає перейменований код. Це
дорожче — вмикайте, коли зачепили спільний код.

Наприкінці вона називає наступну команду — `/gku:fix`, якщо є що виправляти, і `/gku:pr`, якщо
немає. Сама вона нічого не застосовує.

### `/gku:fix` — виправити те, що знайшла рецензія

```
/gku:fix
/gku:fix REVIEW.md
/gku:fix експорт падає, коли в кафедри немає завідувача
/gku:fix --nits
```

Друга половина `/gku:review`. Бере знахідки й застосовує їх: **за замовчуванням блокери й
попередження**, по коміту на кожну, а тоді перезапускає тести. Дрібниці лише перелічуються, а не
застосовуються — це справа смаку, і вони ховають справжні зміни у діфі, який комусь читати. Щоб
узяти і їх, додайте `--nits`.

Працює трьома способами — саме тому нею можна **починати нову сесію**, а не лише продовжувати
попередню:

- **без аргументів** — бере знахідки з `/gku:review`, запущеної раніше в цій розмові, а якщо їх
  немає — проводить цю рецензію тут-таки;
- **з файлом** — `REVIEW.md` або будь-який markdown із переліком знахідок;
- **з реченням** — виправляє рівно те, що ви описали, і нічого більше.

**Кожну знахідку вона звіряє з кодом, перш ніж щось редагувати**, зокрема й ту, яку сама ж
сформулювала хвилину тому. Знахідки застарівають: файл переїхав, хтось уже виправив, або
твердження від початку було хибним. Кожна повертається як *виправлено*, *уже вирішено*, *не
підтверджується* — з доказом — або *потребує вашого рішення*.

Застосовує **найменшу зміну, яка закриває знахідку**, без принагідних рефакторингів, і ніколи не
надсилає зміни. Якщо «виправлення» насправді вимагає перепроєктування, вона зупиняється на цій
знахідці й каже про це, а не будує нишком щось більше.

> Вона навмисно не перезапускає рецензію після себе. Рецензія → виправлення → рецензія →
> виправлення — це цикл, який з'їдає ліміт заради дедалі меншої користі. Вона називає наступну
> команду; обираєте ви.

### `/gku:pr` — відкрити пул-реквест

```
/gku:pr
/gku:pr "Не об'єднувати однойменні кафедри в експорті статистики"
/gku:pr --draft
/gku:pr --dry-run
```

Відкриває пул-реквест для поточної гілки або оновлює вже прив'язаний до неї. Надсилає коміти,
які ви вже зробили; ніколи не комітить за вас, не зливає гілки й не робить force-push.

**Найцінніше в ній: перевірка, що гілка читається як один пул-реквест.** Гілка, у якій є фіча,
*і* стороннє виправлення, *і* переформатування — це три рецензії, що вдають одну, і саме там
тихо зникає якість рецензування. Знайшовши таке, навичка зупиняється, показує знайдені групи —
речення про кожну, її коміти, її файли — і питає:

- **усе одно відкрити один пул-реквест** — часто це правильна відповідь, коли причеплене
  маленьке; або
- **зупинитися, щоб ви розділили гілку самі** — з переліком того, які коміти куди пішли б.

Сама гілку вона не ділить. Переписувати вашу історію — не її рішення.

Багато файлів з однією метою, або реалізація разом із тестами та міграцією, — це **одна** зміна,
і на такі вона не скаржиться.

Опис пишеться з реального діфу та з `.github/pull_request_template.md` вашого репозиторію, якщо
він є, а заголовок — у стилі, який вона читає з ваших нещодавно злитих пул-реквестів. Розділ про
тестування каже, що саме запускали, і **чесно зізнається, коли не запускали нічого**. Оновлення
наявного пул-реквесту ніколи не перезаписує мовчки опис, який писала людина.

### `/gku:pr-review` — відрецензувати чужий пул-реквест

```
/gku:pr-review 42
/gku:pr-review https://github.com/grinchenkoedu/local_gdo/pull/42
```

Викачує пул-реквест в окреме робоче дерево (worktree) — ваша власна робота лишається
недоторканою — і рецензує його як належить.

Вона свідомо **пропускає те, що вже покрив автоматичний рецензент** (форматування, назви,
стиль) і шукає те, чого автоматична рецензія структурно не бачить: що станеться, якщо щось
обірветься на півдорозі; цикли, які не завершуються на дивних даних; двоє людей, що натиснули
одночасно; хто ще викликає змінений код; і чи робить зміна те, що обіцяє її опис.

Лише два рівні: **BLOCKER** (з конкретним сценарієм відмови — немає сценарію, немає блокера) і
**SMELL**. Результат приходить у чат, коротко. У GitHub нічого не публікується — що саме
сказати, вирішуєте ви.

> Схвалення від автоматичного рецензента не є доказом того, що код правильний. Він
> налаштований на точність щодо стилю й спокійно схвалює зміни зі справжніми помилками. Ця
> навичка вважає таке схвалення відсутністю інформації.

### `/gku:pr-resolve` — опрацювати коментарі до вашого пул-реквесту

```
/gku:pr-resolve https://github.com/grinchenkoedu/local_gdo/pull/42
/gku:pr-resolve 42
/gku:pr-resolve 42 --dry-run
```

Для **вашого власного** пул-реквесту. **Посилання працює звідусіль** — з будь-якого каталогу, з
іншого проєкту або взагалі поза репозиторієм: репозиторій визначається з URL, наявний локальний
клон використовується повторно, а якщо його немає — створюється, і вам скажуть де. Голий номер
працює лише всередині клону того репозиторію, якому належить пул-реквест. Збирає всі коментарі й — це найважливіше — **виносить
вердикт щодо кожного, перш ніж змінювати бодай рядок коду**:

- **згоден** → найменше виправлення, окремим комітом;
- **не згоден** → код не змінюється, натомість ввічлива відповідь із файлом і рядком, які це
  спростовують;
- **незрозуміло** → питає вас, збираючи всі такі питання в одне звернення.

Далі відправляє зміни й відповідає в кожній гілці обговорення.

Рецензенти — і люди, і роботи — іноді помиляються. Виправлення впевнено сформульованого хибного
зауваження — це якраз спосіб внести справжню помилку. Почніть із `--dry-run`, щоб побачити
вердикти до будь-яких змін.

### `/gku:verify` — довести, що працює

```
/gku:verify
/gku:verify 42
/gku:verify --tests-only
```

«Тести проходять» і «функція працює» — два різні твердження. Ця навичка робить обидва окремо.

Вона запускає набір тестів проєкту (цитуючи справжній рядок результату, а не «тести пройшли»), а
тоді **запускає саму річ** — команду, сторінку, функцію — і перевіряє результат.

Найкорисніше в ній — чесність щодо того, чого перевірити не вдалося. Кожна пропущена перевірка
отримує категорію і спосіб її розблокувати, а **«не можу сказати» — це коректний висновок**.
Впевнене «працює», що спирається на три пропущені перевірки, гірше за відсутність відповіді.

## Як писати файл задачі

Для всього, що більше за одне речення, опишіть задачу в markdown-файлі й передайте його.
Обов'язкового формату немає — це читає мовна модель, тож звичайний зрозумілий текст цілком
годиться. Робочий приклад:

```markdown
# Експорт індивідуального плану за показниками

## Що потрібно
Фоновий експорт статистики індивідуальних планів у xlsx, два аркуші:
один за показниками, другий — з деталізацією наукової роботи.

## Навіщо
Адміністратори факультетів рахують це вручну щосеместру.

## Деталі
- Використати наявний механізм фонових експортів — без нової інфраструктури.
- Рядки групуються за показником, потім факультетом, потім кафедрою.
- Кафедри різних факультетів можуть мати однакову назву; їх не можна об'єднувати.

## Готово, коли
- [ ] Адміністратор може замовити експорт зі сторінки статистики
- [ ] У файлі є обидва аркуші, числа є числами (сортуються в Excel)
- [ ] Однойменні кафедри різних факультетів лишаються окремими
```

Тримайте їх у `.tasks/` — `/gku:plan` пише туди, `/gku:implement` читає й оновлює. Додайте `.tasks/` до
`.gitignore`, якщо не хочете зберігати описи задач у системі контролю версій.

**Будьте конкретні щодо того, що означає «готово».** Цей перелік стає критеріями готовності:
саме за ними працює `/gku:implement` і саме їх перевіряє `/gku:verify`. Розмиті критерії дають розмитий
результат.

## Використання на тарифі Pro

Claude Code на підписці Pro має ліміти використання, які періодично поновлюються. Ці навички
писалися з огляду на це — дорогих підходів (рої паралельних агентів, фонові процеси, читання
цілого репозиторію) тут свідомо немає.

Як вони заощаджують:

- **Жодних субагентів за замовчуванням.** Щонайбільше один — і лише коли ви попросите `--deep`.
- **Стек визначається один раз**, кешується у `.claude/repo-profile.json` і використовується
  всіма навичками. Додайте цей файл до `.gitignore` — він описує вашу машину.
- **Читання обмежене.** Щонайбільше п'ять файлів цілком, решта — за змінами. Якщо навичка
  оцінювала файл лише за diff, вона про це скаже.
- **Відповіді — у чаті**, а не у згенерованих звітах. Файл створюється лише за наявності
  блокера або на ваш запит `--report`.
- **`/gku:implement` можна продовжити**, тож досягнутий ліміт коштує вам лише часу.

Практичні поради:

1. **Лишайтеся на Sonnet.** Нічому тут не потрібна більша модель. Перевірити — `/model`.
2. **Використовуйте `/clear` між різними задачами.** Довга розмова надсилається наново з кожним
   повідомленням, тож стороння тригодинна історія робить дорожчим кожен запит.
3. **`/gku:review` — часто, `--deep` — рідко.** Звичайний варіант ловить більшість. `/gku:fix`
   навмисно не рецензує після себе: одна рецензія, один прохід виправлень — і далі ви вирішуєте.
   Ганяти їх по колу — найлегший спосіб спалити ліміт заради дедалі меншої користі.
4. **Краще `/gku:implement` із написаним файлом задачі**, ніж із розмитим реченням: з першого разу
   виходить правильно частіше, а переробка коштує дорожче за добрий опис.
5. **Якщо ліміт скінчився посеред роботи — не починайте спочатку.** Дочекайтесь поновлення й
   використайте `--continue`.

## Якщо щось не працює

**Команди не з'явилися після встановлення.**
Перезапустіть Claude Code. Перевірте через `/plugin`, що `gku@grinchenkoedu` є у списку.

**`/gku:pr-review` не знаходить пул-реквест.**
Перевірте `gh auth status`. Для приватного репозиторію потрібен доступ, а токену — область
`repo`. Увійдіть наново: `gh auth login --scopes "repo,read:org"`.

**Навичка неправильно визначила команду тестів.**
Вона кешує визначене. Видаліть `.claude/repo-profile.json` і запустіть знову або передайте
`--reprofile`. Якщо справжня команда проєкту лежить у незвичному місці — впишіть її в
`AGENTS.md` репозиторію: навички читають цей файл.

**`/gku:implement` відмовляється починати.**
Зазвичай через незакомічені зміни, яких вона не робила. Закомітьте або сховайте їх (`git
stash`) — вона не будуватиме поверх роботи, за яку не може відповідати.

**`/gku:pr` каже, що моя гілка схожа на кілька пул-реквестів.**
Вона знайшла групи комітів, між якими немає спільної нитки. Прочитайте ці групи: якщо причеплене
маленьке й достатньо дотичне — скажіть відкрити один пул-реквест, це нормальна відповідь, а не
обхідний шлях. Якщо ж це справді різні зміни, вона підкаже, які коміти куди належать, але гілку
ви ділите самі — вашу історію вона не переписує.

**`/gku:fix` нічого не змінила й каже, що знахідки не підтверджуються.**
Так і має бути. Вона звіряє кожну знахідку з кодом, а рецензія — зокрема й її власна — інколи
помиляється щодо вашого коду. Прочитайте доказ до кожної знахідки; якщо ви з ним не згодні —
скажіть, і вона виправить.

**`/gku:verify` каже «не можу сказати».**
Це задумано, а не збій. Подивіться на заблоковані перевірки та їхні категорії — до кожної є
однорядкова підказка. Категорія `HOSTED` означає, що коду потрібен застосунок-господар (плагін
Moodle не запускається сам по собі) — це факт про проєкт, а не проблема, яку треба виправляти.

**Навичка каже, що перейшла на хост замість Docker.**
Демон не запущений або Docker не встановлено. Запустіть Docker Desktop і видаліть
`.claude/repo-profile.json`, щоб визначення відбулося наново. Це варто зробити: на хості ви
перевіряєте код на тих версіях, які випадково є на вашій машині, а для цих проєктів це часто
не та версія, під яку вони написані.

**«make: command not found».**
`make` не входить до стандартної інсталяції Windows — і навички не мали б його викликати: вони
зберігають команду зсередини `Makefile`, а не сам виклик `make`. Видаліть
`.claude/repo-profile.json` і запустіть знову. Якщо все ж потрібен `make`:
`winget install ezwinports.make`.

**На Windows: команда Docker падає з дивним шляхом на кшталт `C:/Program Files/Git/app`.**
Git Bash підмінив шлях усередині контейнера. У профілі ця команда має зберігатися з
`MSYS_NO_PATHCONV=1` на початку; видаліть `.claude/repo-profile.json` і дайте визначити наново.
Проєкти з `docker-compose.yml` цього уникають узагалі, бо в `docker compose exec` немає
аргументу монтування, який можна підмінити.

**На Windows: у diff змінилися геть усі рядки.**
Це закінчення рядків, а не справжні зміни — файл перетворився між CRLF і LF. Перевірте
`git config core.autocrlf`, перш ніж рецензувати це як реальні зміни.

**Навичка просить видалити worktree.**
Worktree — це додаткові робочі копії в каталогах на кшталт `../<repo>-pr-42`. Їх безпечно
видаляти, коли закінчили. Переглянути наявні: `git worktree list`.

## Як додати свою навичку

Створіть `plugins/gku/skills/<назва>/SKILL.md` з полями `name` і `description` у
frontmatter.

Дотримуйтесь домовленостей наявних навичок — саме вони роблять усе це придатним для обмеженого
тарифу:

- жодних субагентів за замовчуванням, щонайбільше один за прапорцем `--deep`;
- жодних фонових процесів чи роїв агентів;
- читати зміни, а не репозиторій, із явним обмеженням;
- відповідати в чаті, файл створювати лише за блокера або на запит;
- жодних абсолютних шляхів з вашої машини у `SKILL.md`;
- нічого специфічного для одного репозиторію — читайте домовленості самого проєкту.

Спільна логіка визначення проєкту — у `plugins/gku/reference/repo-profile.md`. Якщо вашій
навичці треба щось знати про проєкт, додайте це туди, а не визначайте окремо.
