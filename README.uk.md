Набір навичок (skills) для [Claude Code](https://claude.com/claude-code) на звичайний робочий
день розробника: розібратися, що треба зробити, зробити, перевірити себе, відрецензувати чужий
пул-реквест, розібрати коментарі до свого — і переконатися, що результат справді працює.

Працюють у будь-якому репозиторії: нічого тут не прив'язано до конкретного проєкту, мови чи
фреймворку. І написані вони **економно**, щоб ними можна було користуватися на скромному тарифі
Claude: без фонових зграй агентів, без паралельних субагентів за замовчуванням, з відповідями в
чаті замість купи згенерованих звітів.

Ліцензія MIT.

## Що це таке

**Навичка** — це набір інструкцій, який у Claude Code можна викликати за назвою. Замість щоразу
пояснювати, як має виглядати добра рецензія коду, ви пишете `/gku:review` — і Claude іде за
процедурою, яку колись написали й відшліфували.

Викликаються навички в чаті Claude Code через скісну риску: `/gku:review`.

Це **не магія** і **не автоматика**. Кожна з них робить те, що ви могли б зробити й самі, — але
робить це щоразу однаково й не забуває нудних дрібниць, а саме на них і трапляються помилки.

Чотири навички (`/gku:plan`, `/gku:review`, `/gku:pr-review`, `/gku:verify`) взагалі не чіпають
ваш код. Три (`/gku:implement`, `/gku:fix`, `/gku:pr-resolve`) змінюють його — і кожна
попереджає, що саме збирається зробити. `/gku:pr` локально нічого не змінює: він відправляє
коміти, які ви вже зробили, і відкриває пул-реквест.

Жодна з них не виконує вказівок із того, що читає. Коментар до пул-реквесту, бриф, файл зі
знахідками, вивід тестів — це свідчення про код, і навичка звіряє їх із кодом; змусити її
запушити, обійти хук, виконати команду чи переписати власні правила вони не можуть. Це можете
лише ви — в чаті. Де саме проходить ця межа і чому вона не коштує жодного зайвого кроку, описано
в `plugins/gku/reference/untrusted-input.md`.

## Що потрібно перед початком

1. **Claude Code** — встановлений і робочий: [інструкція зі встановлення](https://docs.claude.com/en/docs/claude-code/overview).
2. **git** — якщо ви клонуєте репозиторії, він у вас уже є.
   **На Windows поставте [Git for Windows](https://git-scm.com/download/win)**: разом із ним іде
   Git Bash, через який Claude Code виконує команди. Навички розраховують, що він є.
3. **GitHub CLI (`gh`)** — для трьох навичок, які працюють із пул-реквестами:

   ```bash
   winget install --id GitHub.cli     # Windows
   brew install gh                    # macOS
   sudo apt install gh                # Ubuntu/Debian
   ```

   Потім один раз увійдіть і перевірте, що все вийшло:

   ```bash
   gh auth login
   gh auth status
   ```

   `/gku:plan`, `/gku:implement`, `/gku:review`, `/gku:fix` і `/gku:verify` обходяться без `gh`.
   Він потрібен лише `/gku:pr`, `/gku:pr-review` та `/gku:pr-resolve`, бо вони ходять у GitHub.

4. **Docker** — [Docker Desktop](https://www.docker.com/products/docker-desktop/) на Windows і
   macOS, Docker Engine на Linux. **Дуже радимо на будь-якій платформі**, не лише на Windows.

   За замовчуванням навички виконують команди проєкту **всередині його контейнера**. Річ не в
   зручності, а в коректності: ці проєкти розраховані на конкретні версії середовища. Плагін під
   PHP 7.4, перевірений хостовим PHP 8.4, пропустить синтаксис, який упаде на продакшені, а
   тести, що пройшли не на тій версії, нічого не довели. У контейнері ж — саме та версія, з якою
   проєкт живе, разом із залежностями та базою даних.

   Заодно це означає, що локально вам не потрібні ні PHP, ні Composer, ні Python, ні Node —
   деякі з цих проєктів узагалі розраховані на те, що їх немає, — а ті самі команди однаково
   працюють на Windows, macOS, Linux і в WSL.

   Без Docker навички теж працюють: вони візьмуть те, що є на вашій машині, і скажуть про це.
   Якщо версії не збігаються з проєктними, до «зеленого» прогону ставтеся з підозрою.

**На Windows усе працює.** Користуйтеся Git Bash, як у пункті 2. Під час першого запуску навички
визначають платформу й зберігають команди, які на ній працюють. WSL теж підходить і поводиться як
Linux.

## Встановлення

У Claude Code виконайте дві команди:

```
/plugin marketplace add grinchenkoedu/claude-skills
/plugin install gku@grinchenkoedu
```

Готово. Наберіть `/` — і в списку з'являться `/gku:plan`, `/gku:implement`, `/gku:review`,
`/gku:fix`, `/gku:pr`, `/gku:pr-review`, `/gku:pr-resolve` та `/gku:verify`.

### Оновлення

Навички регулярно допрацьовуються. Щоб підтягнути останню версію:

```
/plugin marketplace update grinchenkoedu
/reload-plugins
```

Перша команда оновлює маркетплейс із GitHub, друга перезавантажує навички в поточній сесії —
перезапускати Claude Code не доведеться.

Якщо не хочеться цим перейматися, `/plugin` відкриває менеджер плагінів: там видно, що
встановлено, і звідти ж можна оновитися.

**Чому оновлення доходять завжди.** У маніфесті цього плагіна навмисно немає поля `version`.
Тоді Claude Code вважає новою версією **кожен коміт**, і оновлення завжди приносить найсвіжіше.
Якби версія була вказана, ви не отримували б нічого, доки її не піднімуть, — а про це легко
забути й місяцями непомітно сидіти на старих навичках.

<details>
<summary>Якщо ви встановлювали копіюванням файлів</summary>

Скопіюйте їх ще раз — за джерелом ніхто не стежить:

```bash
cd claude-skills && git pull
cp -R plugins/gku/skills/* ~/.claude/skills/
cp -R plugins/gku/reference ~/.claude/skills/reference
cp -R plugins/gku/templates ~/.claude/skills/templates
```

Це головна причина обрати встановлення через плагін.
</details>

<details>
<summary>Встановлення без системи плагінів</summary>

macOS, Linux або Git Bash на Windows:

```bash
git clone https://github.com/grinchenkoedu/claude-skills.git
mkdir -p ~/.claude/skills
cp -R claude-skills/plugins/gku/skills/* ~/.claude/skills/
cp -R claude-skills/plugins/gku/reference ~/.claude/skills/reference
cp -R claude-skills/plugins/gku/templates ~/.claude/skills/templates
```

Windows PowerShell:

```powershell
git clone https://github.com/grinchenkoedu/claude-skills.git
New-Item -ItemType Directory -Force "$HOME\.claude\skills" | Out-Null
Copy-Item -Recurse -Force claude-skills\plugins\gku\skills\* "$HOME\.claude\skills\"
Copy-Item -Recurse -Force claude-skills\plugins\gku\reference "$HOME\.claude\skills\reference"
Copy-Item -Recurse -Force claude-skills\plugins\gku\templates "$HOME\.claude\skills\templates"
```

Через плагін оновлюватися простіше. Цей спосіб — лише коли на те є причина.

> **Дві відмінності цього способу.** Навички **не отримують префікса** — вони встановлюються як
> `/review`, `/init`, `/verify`, а не `/gku:review`. Тож **`/init`, `/review` і `/verify`
> заступають однойменні команди самого Claude Code**, причому `/init` робить схожу річ, і ви не
> зрозумієте, яку саме з двох викликали. Щоб зберегти оригінальні команди, перейменуйте каталоги
> в `~/.claude/skills/`.
</details>

## Навички

Ідуть у тому ж порядку, що й сама робота:

```
   /gku:init ──▶ /gku:plan ──▶ /gku:implement ──▶ /gku:review ⇄ /gku:fix ──▶ /gku:pr
(раз на репозиторій)                                                            │
                                       ┌────────────────────────────────────────┤
                                       ▼                                        ▼
                                /gku:pr-review                          /gku:pr-resolve
                            (чужий пул-реквест)                 (коментарі до вашого)
                                       │                                        │
                                       └───────────────▶ /gku:verify ◀──────────┘
```

| Команда | Що робить | Змінює код? |
|---|---|---|
| `/gku:init` | Пише `CLAUDE.md` для репозиторію — команди й правила його родини | **Так** (один файл) |
| `/gku:plan` | Перетворює запит на конкретний план, звірений зі справжнім кодом | Ні |
| `/gku:implement` | Виконує план крок за кроком і відмічає зроблене | **Так** |
| `/gku:review` | Перевіряє ваші зміни, перш ніж ви їх відправите | Ні |
| `/gku:fix` | Розслідує симптом або застосовує знахідки рецензії — по коміту на кожну | **Так** |
| `/gku:pr` | Відкриває пул-реквест для гілки або оновлює наявний | Ні (відправляє ваші коміти) |
| `/gku:pr-review` | Як слід рецензує чужий пул-реквест | Ні |
| `/gku:pr-resolve` | Розбирає коментарі рецензентів до *вашого* пул-реквесту | **Так** |
| `/gku:verify` | Запускає тести й пробує результат наживо | Ні |

Користуватися всіма, та ще й саме в такому порядку, не обов'язково. Навіть сам лише `/gku:review`
перед кожним пушем уже окупається.

## Приклад від початку до кінця

Скажімо, вам повідомили: *експорт статистики зливає докупи дві кафедри з однаковою назвою.*

**1. Розібратися, що насправді сталося.**

```
/gku:plan експорт статистики об'єднує кафедри з однаковою назвою
```

> **Про лапки.** Вони не потрібні. Те, що ви набираєте, потрапляє до навички як звичайний
> текст — оболонки (shell) тут немає, тож нічого не треба екранувати, і апострофи не заважають.
> Лапки стають у пригоді лише тоді, коли після опису йде прапорець і треба показати, де опис
> закінчується: `/gku:implement "додати експорт у CSV" --continue`.

Claude знайде код експорту, прочитає його, перевірить у базі, чи справді є однойменні кафедри, і
запише план у `.tasks/export-department-collision.md`: причина, виправлення, критерії готовності
та кроки по порядку. Прочитайте його. **Якщо план хибний, скажіть про це одразу** — поправити
план набагато дешевше, ніж наполовину зроблену зміну.

**2. Зробити.**

```
/gku:implement .tasks/export-department-collision.md
```

Навичка створить гілку, пройде кроки один за одним, відмітить кожен у файлі задачі й запустить
тести. Кожну правку видно, і зупинити можна будь-якої миті.

> **Якщо посеред роботи скінчиться ліміт — нічого страшного.** Виконані кроки вже відмічені у
> файлі задачі. Коли ліміт поновиться,
> `/gku:implement .tasks/export-department-collision.md --continue` підхопить рівно з того місця,
> де зупинилося.

**3. Перевірити себе.**

```
/gku:review
```

Ви отримаєте короткий список: блокери, які треба виправити першими, попередження, на які варто
глянути, і дрібниці, які можна й пропустити. Наприкінці навичка називає, що запускати далі, —
щоб ви не лишилися сам на сам зі списком.

**4. Виправити знайдене.**

```
/gku:fix
```

Навичка бере знахідки з щойно виконаної рецензії, **звіряє кожну зі справжнім кодом**, перш ніж
щось чіпати, — щось уже виявиться виправленим, а щось просто хибним, — а тоді береться за
блокери й попередження, по коміту на кожне, і перезапускає тести. Дрібниці вона лише перелічує;
щоб узяти й їх, додайте `--nits`.

> Та сама команда працює й «з чистого аркуша». `/gku:fix експорт об'єднує однойменні кафедри` у
> новій сесії спершу розслідує повідомлення — знайде код, відтворить проблему, доведе причину — і
> тоді виправить, а не віддасть вам план, який іще треба запускати.

**5. Відкрити пул-реквест.**

```
/gku:pr
```

Навичка прочитає гілку цілком, перевірить, що вона **читається як один пул-реквест** — і спершу
перепитає, якщо це схоже на фічу з причепленим стороннім виправленням, — а тоді відправить коміти
й напише опис за реальним діфом, за шаблоном вашого репозиторію, якщо він є.

**6. Розібрати коментарі рецензента.**

Автоматичний рецензент залишив коментарі. Замість правити кожен руками:

```
/gku:pr-resolve 42
```

Спершу навичка **звірить кожен коментар зі справжнім кодом**, потім виправить те, що слушне, з
доказами заперечить там, де рецензент помилився, і спитає вас про справді неоднозначне. Один
коміт на виправлення, одна відповідь на коментар.

**7. Переконатися, що працює.**

```
/gku:verify
```

Запустить тести *і* сам експорт, а тоді дасть висновок — разом із чесним переліком того, що
перевірити не вдалося.

## Кожна навичка докладно

### `/gku:init` — дати репозиторію `CLAUDE.md`

```
/gku:init
/gku:init --refresh
/gku:init --dry-run
```

`CLAUDE.md` читається на початку кожної сесії в репозиторії, тому саме там місце командам збірки
й тестів і тим кільком правилам, які тут справді порушують. `/gku:init` визначає родину проєкту —
плагін Moodle, PHP-застосунок, CMS, Python, — підставляє справжні команди й додає домовленості
цієї родини, її правила безпеки, пріоритети дизайну (спершу читабельність, потім
супроводжуваність, розширюваність і аж тоді ефективність) і те, де має виконуватися тривала
робота.

Спільна частина лежить між маркерами:

```markdown
<!-- toolkit:begin family-rules -->
...підтримується /gku:init...
<!-- toolkit:end family-rules -->
```

`--refresh` замінює **лише** цей блок, тож усе, що ви дописали руками, лишається.

Якщо `CLAUDE.md` уже є, навичка спершу його **читає й оцінює**: коли команди правильні, а блок
родини актуальний, вона відповість «уже все гаразд» і нічого не запише — перетрушувати добрий
файл ніякий не прогрес. Застарілу команду або правило, якому суперечить код, вона перелічить вам,
а не виправить мовчки. Файл без маркерів ніколи не перезаписується — навичка спершу спитає.

Ще вона лишає заглушку `AGENTS.md` з посиланням на `CLAUDE.md`, щоб інші агенти знаходили ті
самі правила без другої копії, яка з часом розійдеться з першою. Саме заглушку, а не симлінк: на
Windows git викачує симлінки як звичайні текстові файли.

Запускайте раз на репозиторій — і ще раз, коли правила родини стануть кращими.

### `/gku:plan` — розібратися, що робити

```
/gku:plan студенти не можуть завантажити свій індивідуальний план
/gku:plan .tasks/new-grade-export.md
/gku:plan --review .tasks/proposed-approach.md
```

Дайте їй речення або вкажіть markdown-файл із докладнішим описом. Вона розбереться, про що
йдеться — про помилку, нову можливість, питання чи проблему з даними (відповіді на це геть
різні), — а тоді прочитає код і звірить свої припущення зі справжніми даними, перш ніж щось
пропонувати.

Результат лягає в `.tasks/<назва>.md`: причина або дизайн, критерії готовності, кроки по порядку
і те, як перевірити результат. Для вебзастосунку дизайн ще й каже, які кроки виконуються у фоні,
а не в запиті, — тим механізмом, який у проєкті вже є.

`--review` — для файлу, де рішення **вже запропоноване**: тоді навичка оцінює цю пропозицію, а
не вигадує власну.

**Коду вона не пише.** Користуйтеся нею, коли ще не певні, яка зміна правильна, або коли підхід
треба з кимось узгодити, перш ніж будувати. А якщо щось просто зламане й треба полагодити,
`/gku:fix` проводить те саме розслідування й одразу діє.

### `/gku:implement` — зробити

```
/gku:implement .tasks/export-department-collision.md
/gku:implement додати експорт студентів у CSV
/gku:implement .tasks/big-task.md --continue
```

Працює послідовно у вашому робочому дереві — без фонових агентів, нічого прихованого. Створює
гілку, якщо ви на головній, проходить кроки по черзі, перевіряє кожну зміну одразу, пише тести й
запускає набір тестів.

**Файл задачі водночас є журналом прогресу.** Кожен виконаний крок відмічається з приміткою, що
саме зроблено, — тому `--continue` і працює після перерви.

Навичка не виходить за межі задачі. Якщо помітить, що поламане щось іще, скаже про це наприкінці,
а не виправить тишком: реалізацію, яка розповзається, ніхто не зможе відрецензувати.

### `/gku:review` — перевірити себе

```
/gku:review
/gku:review --deep
/gku:review --report
```

**Та, якою варто користуватися щодня.** Запускайте перед пушем. Навичка читає ваші зміни,
застосовує домовленості *вашого* репозиторію (з `AGENTS.md`, `CLAUDE.md` чи що там є в проєкті)
і видає перелік за рівнем важливості:

- **BLOCKER** — не відправляйте. Закомічений пароль, втрата даних, перейменована функція, яку
  досі десь викликають, неекранований користувацький ввід, зміна в Moodle без підняття версії у
  `version.php`.
- **WARNING** — виправте, перш ніж просити рецензію. Логіка без тестів, необроблена помилка,
  цикл, який може не скінчитися.
- **NIT** — на ваш розсуд.

Вона також перевіряє, чи ваші **тести справді щось доводять**: тест без справжнього твердження
або такий, що замокав саме те, що ви змінили, проходить і нічого не доводить.

До кожної рецензії входить **перевірка безпеки** за добре відомими вадами: значення із запиту, що
потрапляє в SQL, оболонку, файлову систему чи на сторінку без екранування; точка входу без
перевірки входу чи прав; запис, який будь-хто прочитає, підставивши інший id; форма, прив'язана
прямо до моделі; зміна стану без CSRF-токена; закомічений секрет; завантажений файл, збережений
там, де сервер його виконає; сервер, який ходить за URL на вибір користувача; слабкі токени й
хешування; залежність з опублікованою вразливістю. Повний перелік — із шаблоном коду та доказом
для кожної — лежить у `plugins/gku/reference/security-checklist.md`. Знахідка називає рядок і
один вхід, який її показує — одинарну лапку, `../`, тег `<b>`, — і далі цього справа ніколи не
йде. Останній рядок рецензії каже, які частини перевірки виконано, тож пропущену частину видно, а
не замовчано.

Якщо в проєкті є команда лінтера, навичка **проганяє через нього змінені файли** й повідомляє про
синтаксичну помилку як про блокер. У репозиторії без тестів і без робочого CI це єдина механічна
перевірка між синтаксичною помилкою та живим сайтом. Вона також попередить, якщо лінтер працює
на новішій версії мови, ніж та, під яку написано проєкт: парсер PHP 8 нічого не скаже про проєкт,
який декларує `>=7.4`.

`--deep` дозволяє одному помічнику додатково перевірити, хто викликає перейменований код. Це
дорожче — вмикайте, коли зачепили спільний код.

Наприкінці вона називає наступну команду: `/gku:fix`, якщо є що виправляти, і `/gku:pr`, якщо
немає. Сама вона нічого не застосовує.

### `/gku:fix` — знайти, що не так, і виправити

```
/gku:fix
/gku:fix .gku/reports/review-my-branch-20260824-143201.md
/gku:fix експорт падає, коли в кафедри немає завідувача
/gku:fix --nits
/gku:fix --dry-run
```

Дві роботи в одній команді, бо на практиці це одна робота.

**Коли є знахідки**, вона їх застосовує — **за замовчуванням блокери й попередження**, по коміту
на кожну, — а тоді перезапускає тести. Дрібниці лише перелічує: це справа смаку, а в діфі, який
комусь читати, вони ховають справжні зміни. `--nits` бере і їх. Це та половина, яку `/gku:review`
навмисно лишає незробленою.

**Коли є симптом** — речення про те, що зламалося, — вона **спершу розслідує**, як `/gku:plan`:
розбирається, чи це баг, фіча, питання чи проблема з даними; знаходить код; відтворює; доводить
причину. І лише тоді щось редагує.

Від `/gku:plan` її відрізняє те, що далі: **коли причина доведена, а виправлення очевидне, вона
діє.** Ні файлу плану, ні погодження вашого ж баг-репорту. Каже у двох-трьох рядках, що знайшла,
і виправляє. Питає лише тоді, коли відповідь змінює саме виправлення: два рівноцінні варіанти,
причина поза цією гілкою або те, що виявилося фічею, а не багом. *Питання, на яке можна
відповісти, прочитавши ще трохи коду, — не питання.*

Тому з неї зручно **починати нову сесію з одним лише баг-репортом**. У розмові до того може не
бути нічого:

- **без аргументів** — знахідки з `/gku:review`, запущеної раніше в цій розмові, а коли їх
  немає — та сама рецензія тут-таки;
- **з файлом** — звіт із `.gku/reports/` або будь-який markdown зі списком знахідок;
- **з реченням** — розслідує, потім виправляє.

Вона чітко розрізняє **доведену причину** та **гіпотезу** і каже, на що саме спиралася. Якщо
симптом вдалося відтворити, після виправлення вона повторює те саме відтворення: зелені тести не
доводять, що ваш баг зник, — а те, що падало й більше не падає, доводить.

**Кожну знахідку вона звіряє з кодом, перш ніж щось редагувати**, — і ту, яку сама сформулювала
хвилину тому, теж. Знахідки застарівають: файл переїхав, хтось уже виправив або твердження від
початку було хибним. Кожна повертається як *виправлено*, *уже вирішено*, *не підтверджується*
(з доказом) або *потребує вашого рішення* — і ті, що не підтвердилися, коштують вам лише рядка у
звіті.

`--dry-run` зупиняється після діагнозу — це `/gku:fix` у ролі `/gku:plan`, якщо вам потрібно
саме це.

Вона вносить **найменшу зміну, яка закриває знахідку**, без принагідних рефакторингів, і ніколи
не пушить. Якщо «виправлення» насправді вимагає перепроєктування, вона зупиняється на цій
знахідці й каже про це, а не тихо будує щось більше.

> Після себе вона навмисно не запускає рецензію ще раз. Рецензія → виправлення → рецензія →
> виправлення — це цикл, який спалює ліміт заради дедалі меншої користі. Вона називає наступну
> команду; обираєте ви.

### `/gku:pr` — відкрити пул-реквест

```
/gku:pr
/gku:pr "Не об'єднувати однойменні кафедри в експорті статистики"
/gku:pr --draft
/gku:pr --dry-run
```

Відкриває пул-реквест для поточної гілки або оновлює той, що вже до неї прив'язаний. Відправляє
коміти, які ви вже зробили; ніколи не комітить за вас, не зливає гілки й не робить force-push.

**Головне в ній — перевірка, що гілка читається як один пул-реквест.** Гілка, де є фіча, *і*
стороннє виправлення, *і* переформатування, — це три рецензії, які вдають одну, і саме тут якість
рецензування тихо зникає. Знайшовши таке, навичка зупиняється, показує групи, які знайшла —
речення про кожну, її коміти, її файли, — і питає:

- **все одно відкрити один пул-реквест** — часто це і є правильна відповідь, коли причіп
  невеликий; або
- **зупинитися, щоб ви розділили гілку самі** — з переліком, які коміти куди пішли б.

Сама вона гілку не ділить. Переписувати вашу історію — не її рішення.

Багато файлів з однією метою або реалізація разом із тестами й міграцією — це **одна** зміна, на
таке вона не скаржиться.

Опис пишеться за реальним діфом і за `.github/pull_request_template.md` вашого репозиторію, якщо
він є, а заголовок — у стилі, який вона вичитує з ваших нещодавно злитих пул-реквестів. Розділ
про тестування каже, що саме запускали, і **чесно зізнається, коли не запускали нічого**.
Оновлюючи наявний пул-реквест, вона ніколи не затирає мовчки опис, який писала людина.

### `/gku:pr-review` — відрецензувати чужий пул-реквест

```
/gku:pr-review 42
/gku:pr-review https://github.com/grinchenkoedu/local_gdo/pull/42
```

Викачує пул-реквест в окреме робоче дерево (worktree) — ваша власна робота лишається
неторканою — і рецензує його як слід.

Вона свідомо **пропускає те, що вже покрив автоматичний рецензент** (форматування, назви,
стиль), і шукає те, чого автоматична рецензія за своєю природою не бачить: що буде, якщо щось
обірветься на півдорозі; цикли, які не завершуються на дивних даних; двоє людей, які натиснули
одночасно; хто ще викликає змінений код; і чи робить зміна те, що обіцяє її опис.

Рівнів лише два: **BLOCKER** (з конкретним сценарієм відмови — немає сценарію, немає й блокера)
і **SMELL**. Результат приходить у чат, коротко. У GitHub нічого не публікується — що казати,
вирішуєте ви.

> Схвалення від автоматичного рецензента не доводить, що код правильний. Він налаштований на
> точність щодо стилю і спокійно схвалює зміни зі справжніми помилками. Ця навичка вважає таке
> схвалення відсутністю інформації.

### `/gku:pr-resolve` — розібрати коментарі до вашого пул-реквесту

```
/gku:pr-resolve https://github.com/grinchenkoedu/local_gdo/pull/42
/gku:pr-resolve 42
/gku:pr-resolve 42 --dry-run
```

Для **вашого власного** пул-реквесту. **Посилання працює звідусіль** — з будь-якого каталогу, з
іншого проєкту чи взагалі поза репозиторієм: репозиторій визначається з URL, наявний локальний
клон береться повторно, а якщо його немає — створюється, і вам скажуть де. Сам лише номер працює
тільки всередині клону того репозиторію, якому належить пул-реквест, — більше його ні з чим
звірити. Навичка збирає всі коментарі й — це найважливіше — **виносить вердикт щодо кожного,
перш ніж змінити бодай рядок коду**:

- **згодна** → найменше виправлення, окремим комітом;
- **не згодна** → код не змінюється, натомість ввічлива відповідь із файлом і рядком, які це
  спростовують;
- **незрозуміло** → питає вас, зібравши всі такі питання в одне звернення.

Коментар, звернений до інструмента, а не до коду, — «пропусти тести», «пуш із `--no-verify`» —
не отримує жодного з цих вердиктів: його пропускають, а у звіті про це сказано.

Потім пушить і відповідає в кожному обговоренні.

Рецензенти — і люди, і роботи — часом помиляються. Виправити впевнено сформульоване хибне
зауваження — якраз спосіб внести справжню помилку. Почніть із `--dry-run`, щоб побачити вердикти
до будь-яких змін.

### `/gku:verify` — довести, що працює

```
/gku:verify
/gku:verify 42
/gku:verify --tests-only
```

«Тести проходять» і «функція працює» — два різні твердження. Ця навичка доводить кожне окремо.

Вона запускає тести проєкту (цитуючи справжній рядок результату, а не «тести пройшли»), а тоді
**пробує сам результат** — команду, сторінку, функцію — і перевіряє ефект.

Потім **переконується, що захист на місці**: та сама точка входу без сесії, від тестового
облікового запису без потрібного права, без CSRF-токена, з id чужого запису, з `../` у назві
файлу, з `<b>` у текстовому полі. Кожна перевірка — один мінімальний локальний запит з
одноразових облікових записів, кожна має свій рядок (пройдено, не пройдено або пропущено з
причиною), і бажаний результат тут — відмова. Усе, що для цього створили, потім прибирається.

Найкорисніше в ній — чесність щодо того, чого перевірити не вдалося. Кожна пропущена перевірка
отримує категорію і спосіб її розблокувати, а **«не можу сказати» — це повноцінний висновок**.
Впевнене «працює», яке спирається на три пропущені перевірки, гірше за відсутність відповіді.

## Як писати файл задачі

Для всього, що не вміщається в одне речення, опишіть задачу в markdown-файлі й передайте його.
Обов'язкового формату немає — це читає мовна модель, тож звичайний зрозумілий текст цілком
годиться. Робочий приклад:

```markdown
# Експорт індивідуального плану за показниками

## Що потрібно
Фоновий експорт статистики індивідуальних планів у xlsx, два аркуші:
один за показниками, другий — з деталізацією наукової роботи.

## Навіщо
Адміністратори факультетів рахують це вручну щосеместру.

## Деталі
- Використати наявний механізм фонових експортів — без нової інфраструктури.
- Рядки групуються за показником, потім факультетом, потім кафедрою.
- Кафедри різних факультетів можуть мати однакову назву; їх не можна об'єднувати.

## Готово, коли
- [ ] Адміністратор може замовити експорт зі сторінки статистики
- [ ] У файлі є обидва аркуші, числа є числами (сортуються в Excel)
- [ ] Однойменні кафедри різних факультетів лишаються окремими
```

Тримайте їх у `.tasks/`: `/gku:plan` пише туди, `/gku:implement` звідти читає й там же оновлює.
Додайте `.tasks/` до `.gitignore`, якщо не хочете тримати описи задач у системі контролю версій.

**Будьте конкретні щодо того, що означає «готово».** Цей список стає критеріями готовності — за
ними працює `/gku:implement`, і їх же перевіряє `/gku:verify`. Розмиті критерії дають розмитий
результат.

## Куди потрапляють звіти

Більшість відповідей лишається в чаті. Коли навичка таки пише файл — `/gku:review`, `/gku:verify`
і `/gku:pr-review` за прапорцем `--report` або коли знайшли блокер, — він потрапляє в один
ігнорований каталог, а не в корінь репозиторію:

```
.gku/reports/review-security-pass-20260824-143201.md
.gku/reports/review-security-pass-20260824-171045.md
.gku/reports/verify-security-pass-20260824-172230.md
.gku/reports/pr-review-pr-118-20260824-093700.md
```

Назва має вигляд `<вид>-<гілка-або-PR>-<час UTC>.md`. Префікс каже, яка навичка це написала, час
не дає другому запуску на тій самій гілці затерти перший, а сортування каталогу за назвою
впорядковує звіти за видом, потім за гілкою, а тоді за часом. Нічого не перезаписується, тож
серія рецензій там накопичується, і їх можна порівняти.

Навички додають `.gku/` до вашого `.gitignore`, коли пишуть перший такий файл: це робочі нотатки
про стан вашого робочого дерева в конкретний момент, а не історія проєкту. Каталог можна видалити
будь-коли — його не читає ніхто, крім вас і `/gku:fix <шлях>`.

## Використання на тарифі Pro

У Claude Code на підписці Pro є ліміти використання, які періодично поновлюються. Ці навички
писалися з огляду на це: дорогих підходів — зграй паралельних агентів, фонових процесів, читання
цілого репозиторію — тут свідомо немає.

Як вони заощаджують:

- **Жодних субагентів за замовчуванням.** Щонайбільше один, і лише коли ви попросите `--deep`.
- **Стек визначається один раз**, кешується у `.claude/repo-profile.json` і використовується
  всіма навичками. Додайте цей файл до `.gitignore` — він описує вашу машину.
- **Читання обмежене.** Щонайбільше п'ять файлів цілком, решта — за діфом. Якщо навичка
  оцінювала файл лише за діфом, вона так і скаже.
- **Відповіді — у чаті**, а не в згенерованих звітах. Файл пишеться лише тоді, коли є блокер або
  ви попросили `--report`, — і йде в `.gku/reports/`, а не в корінь репозиторію (див. [Куди
  потрапляють звіти](#куди-потрапляють-звіти)).
- **`/gku:implement` можна продовжити**, тож вичерпаний ліміт коштує вам лише часу.

Практичні поради:

1. **Лишайтеся на Sonnet.** Більша модель тут нічому не потрібна. Перевірити — `/model`.
2. **Робіть `/clear` між непов'язаними задачами.** Довга розмова надсилається наново з кожним
   повідомленням, тож стороння тригодинна історія робить дорожчим кожен запит.
3. **`/gku:review` — часто, `--deep` — рідко.** Звичайний варіант ловить більшість. `/gku:fix`
   навмисно не рецензує після себе: одна рецензія, один прохід виправлень — і далі вирішуєте ви.
   Ганяти їх по колу — найпростіший спосіб спалити ліміт на дедалі менший зиск.
4. **Краще `/gku:implement` з написаним файлом задачі**, ніж із розмитим реченням: так частіше
   виходить правильно з першого разу, а переробка коштує більше, ніж добрий опис.
5. **Якщо ліміт скінчився посеред роботи — не починайте спочатку.** Дочекайтеся поновлення й
   скористайтеся `--continue`.

## Якщо щось не працює

**Після встановлення команди не з'явилися.**
Перезапустіть Claude Code. Перевірте через `/plugin`, що `gku@grinchenkoedu` є в списку.

**`/gku:pr-review` не знаходить пул-реквест.**
Перевірте `gh auth status`. До приватного репозиторію потрібен доступ, а токену — область
`repo`. Увійдіть наново: `gh auth login --scopes "repo,read:org"`.

**Навичка неправильно визначила команду тестів.**
Вона кешує те, що визначила. Видаліть `.claude/repo-profile.json` і запустіть ще раз або
передайте `--reprofile`. Якщо справжня команда проєкту лежить у незвичному місці, впишіть її в
`AGENTS.md` репозиторію — навички читають цей файл.

**`/gku:implement` відмовляється починати.**
Зазвичай через незакомічені зміни, яких вона не робила. Закомітьте або сховайте їх (`git
stash`): вона не будуватиме поверх роботи, за яку не може відповідати.

**`/gku:pr` каже, що моя гілка схожа на кілька пул-реквестів.**
Вона знайшла групи комітів, які нічого не пов'язує. Прогляньте ці групи: якщо причіп невеликий і
достатньо дотичний — скажіть відкрити один пул-реквест; це нормальна відповідь, а не обхідний
шлях. Якщо ж це справді різні зміни, вона підкаже, які коміти куди належать, але ділити гілку
вам — вашу історію вона не переписує.

**`/gku:fix` нічого не змінила й каже, що знахідки не підтверджуються.**
Так і має бути. Вона звіряє кожну знахідку з кодом, а рецензія — і її власна теж — інколи
помиляється щодо вашого коду. Прочитайте доказ до кожної знахідки; якщо ви з ним не згодні —
скажіть, і вона виправить.

**`/gku:fix` назвала причину «гіпотезою».**
Вона не змогла відтворити симптом, тож чесно розрізняє доведене й виведене з читання коду.
Зважуйте виправлення відповідно. Дайте їй те, на чому проблема відтворюється — id запису,
команду, запит, — і наступного разу гіпотеза стане доведеною причиною.

**`/gku:fix` розслідувала й поставила питання замість виправити.**
Так буває лише тоді, коли відповідь змінює саме виправлення: два рівноцінні варіанти, причина в
коді, якого ця гілка не чіпала, або те, що виявилося фічею, а не багом. Дайте відповідь — і вона
продовжить. Якщо ж вам потрібен лише діагноз без правок, скористайтеся `--dry-run`.

**`/gku:verify` каже «не можу сказати».**
Так і задумано, це не збій. Подивіться на заблоковані перевірки та їхні категорії — до кожної є
однорядкова підказка, як розблокувати. Категорія `HOSTED` означає, що коду потрібен
застосунок-господар (плагін Moodle сам по собі не запускається) — це факт про проєкт, а не
проблема, яку треба виправляти.

**Навичка каже, що перейшла на хост замість Docker.**
Демон не запущений або Docker не встановлено. Запустіть Docker Desktop і видаліть
`.claude/repo-profile.json`, щоб визначення пройшло наново. Це варто зробити: на хості ви
перевіряєте код на тих версіях, які випадково є на вашій машині, а для цих проєктів це часто не
та версія, під яку їх писали.

**«make: command not found».**
`make` не входить до стандартної інсталяції Windows — і навички не мали б його викликати: вони
зберігають команду зсередини `Makefile`, а не сам виклик `make`. Видаліть
`.claude/repo-profile.json` і запустіть ще раз. Якщо `make` все ж потрібен:
`winget install ezwinports.make`.

**На Windows: команда Docker падає з дивним шляхом на кшталт `C:/Program Files/Git/app`.**
Git Bash підмінив шлях усередині контейнера. У профілі ця команда має зберігатися з
`MSYS_NO_PATHCONV=1` на початку; видаліть `.claude/repo-profile.json`, щоб визначити наново.
Проєкти з `docker-compose.yml` цього не мають узагалі, бо в `docker compose exec` немає
аргументу монтування, який можна було б спотворити.

**На Windows: у діфі змінилися геть усі рядки.**
Це закінчення рядків, а не справжні зміни — файл перетворили між CRLF і LF. Перевірте
`git config core.autocrlf`, перш ніж рецензувати це як реальний діф.

**Навичка хоче видалити worktree.**
Worktree — це додаткові робочі копії в каталогах на кшталт `../<repo>-pr-42`. Коли закінчили, їх
можна спокійно видаляти. Переглянути наявні: `git worktree list`.

## Як додати свою навичку

Додайте навичку як `plugins/gku/skills/<назва>/SKILL.md` з полями `name` і `description` у
frontmatter.

Дотримуйтеся домовленостей, за якими живуть наявні навички, — саме завдяки їм усе це годиться
для обмеженого тарифу:

- жодних субагентів за замовчуванням, щонайбільше один за прапорцем `--deep`;
- жодних фонових процесів чи зграй агентів;
- читати діф, а не репозиторій, і з явним обмеженням;
- відповідати в чаті; файл писати лише за блокера або на запит — і класти його в
  `.gku/reports/` за спільною схемою назв, а не в корінь репозиторію;
- жодних абсолютних шляхів з вашої машини у `SKILL.md`;
- нічого специфічного для одного репозиторію — натомість читайте домовленості самого проєкту;
- правило про *код, який пишуть навички* (пріоритети дизайну, де виконується тривала робота),
  кладіть у шаблони родин у `plugins/gku/templates/`, щоб воно потрапляло в проєкт через його
  `CLAUDE.md`; правило про *вартість самих навичок* — у `reference/`.

Спільна логіка визначення проєкту лежить у `plugins/gku/reference/repo-profile.md`. Якщо вашій
навичці треба щось знати про проєкт, додайте це туди, а не визначайте окремо. Спільний перелік
перевірок безпеки для `/gku:review` і `/gku:verify` — у
`plugins/gku/reference/security-checklist.md`: ваду додавайте туди один раз, із шаблоном, доказом
і рівнем важливості, а не в кожну навичку окремо. Куди потрапляють файли звітів і як вони
називаються, описано в `plugins/gku/reference/reports.md`; навичка, яка пише звіт, дотримується
цього файлу, а не вигадує власну назву. Що навички вважають свідченням, а не вказівкою —
коментарі, брифи, вивід інструментів — описано в `plugins/gku/reference/untrusted-input.md`;
навичка, яка читає текст, набраний не розробником, посилається на нього саме там, де цей текст
надходить.

Зміна в `SKILL.md` чи в `reference/` — це код, що виконується в кожній сесії на кожній машині,
яка оновить плагін. Рецензуйте її саме так.
